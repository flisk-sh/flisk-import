## Context

#511 lists 30 detectors. If `import.ts` switches on file name, each new format edits the command, the merge, and the writer. The first three formats also describe the same service (Compose `build: ./api`, `api/Dockerfile`, `api/package.json`). That merge is the hard part, so it is built now, with Procfile as the control that needs no merge.

Flisk already has a service manifest and a bring-your-own container path. Import must produce those, not a second project layout.

## Goals / Non-Goals

**Goals**

- One directory in, one plan out, then a write that is idempotent.
- A detector is a data source. Adding one does not change scan, merge, or write.
- Conflicts and skips are visible. The command does not invent a port or a start command when two files disagree.
- First detectors are different shapes: Compose (multi-service file), Dockerfile (one container), package.json (start script), Procfile (one process per line).

**Non-Goals**

- Running the source tool (`helm template`, `kustomize build`, `docker compose config`).
- Kubernetes, Helm, CI, or language-workspace detectors.
- Choosing a native `--language` provider except where a detector is sure (`package.json` with a Bun or Node start script). Unsure means bring-your-own, recorded in the report.
- Rewriting application source.

## Decisions

### Detector interface, not a file-type switch

Each detector exports `{ id, claim(relPath) -> boolean, parse(absPath, relPath) -> { candidates, skips } }`. `claim` is cheap (file name only). `parse` reads the file. The registry is the list of detectors. `--only` filters that list. An unknown id fails before the walk.

A detector that needs a sibling file (Compose `build: ./api`) records a hint on the candidate (`dir`). It does not open the Dockerfile. Merge and the other detector own that.

### Candidate, then manifest

Detectors emit candidates, never `service.json`. A candidate is `kind: service | job`, a suggested name, a directory key, only the fields it actually knows (image, command, port, env, dependsOn, language), `confidence: high | low`, and `sources: [{ file, detector }]`. Unknown fields are omitted, not filled with defaults.

The writer is the only stage that knows the Flisk layout. That keeps a bad detector from inventing schema. A bring-your-own manifest requires a port in 4000-5999 and a health path, so the writer assigns the next free Flisk port exactly as `flisk resource` does. That is Flisk's port, not an imported claim: a candidate port that is missing or in conflict is never guessed from the sources.

### Merge is precedence plus conflict

Group by directory key, then by normalized name. For each field, higher precedence wins when the other value is missing. Precedence for this change: Compose, then Dockerfile, then package.json, then Procfile. Two present values that differ are a conflict: the plan lists both, the write uses neither for that field, and the report says so.

A Dockerfile or package.json candidate has no service name of its own, so it is anonymous within its directory. It attaches to the single named candidate in that directory (Compose `build: ./api`, or a Procfile-less folder). When the directory has no named candidate, it becomes a service named after the directory. When several named candidates share a directory, an anonymous candidate is not guessed onto one of them: it is reported as skipped.

Procfile has no overlap with the others in the common case, which is why it is the easy detector. It still goes through merge so a later overlap does not need a special case.

### Scan bounds

Walk from the given directory. Honor `.gitignore` (simple patterns: names, globs with `*`, trailing `/`, leading `/`, `!` negation is not supported and is reported). Always skip `.git`, `node_modules`, `vendor`, `target`, `dist`, `.autogenerated`. Cap depth at 8 and files considered at 5000; say so in the report when the cap hits. Do not follow symlinks.

### Write rules

Default is plan, then prompt. `--dry-run` never writes. `--yes` writes. An existing `service.json` is left alone unless `--force`. Re-running with the same inputs and `--force` produces the same files. The report is printed, not written into the manifest.

Layout is `<project>/services/<stack>/<name>/service.json`, where the project is the nearest Flisk project root at or above the target directory, else the target directory itself, and the stack is the kebab-cased name of the target directory.

### Native provider versus bring-your-own

Only a high-confidence mapping sets `language` on the candidate: a package.json `start`/`dev` script that is `bun` or `node`. The plan shows it, but the writer still emits bring-your-own: a native backend makes Flisk generate its own app image, and that was not verified against an imported repo's code. Mapping to a native provider is a later change, with a `flisk up` check. Everything is bring-your-own with the image or command the detector found. The manifest has no field for a bring-your-own start command, so a command is recorded as `dev.command` and the plan says it is not run until an image or Dockerfile exists.

## Risks / Trade-offs

- Precedence will be wrong for some repos. Listing the conflict is the mitigation; guessing a port is not.
- Compose is a large format. The detector covers services, `build`, `image`, `ports`, `environment`, and `depends_on`. `extends` and `profiles` services are skipped and named in the report; YAML anchors are resolved and named.
- Cap and gitignore can hide a service. The report includes the cap and the skip count.

## Migration Plan

No existing command changes. Import is additive. Rollback is not running it; it does not edit a manifest unless `--force`.

## Open Questions

- One landscape or one per nested Compose file. This change emits one landscape and groups candidates by directory. Split landscapes can be a later flag.
- Whether unmappable fields get a comment in `service.json`. This change keeps them in the report only, so the manifest stays schema-valid.

## Implementation notes

- Compose `ports:` gives the container-side port (`8080:3000` is 3000), the same quantity as Dockerfile `EXPOSE`. Several distinct ports means no port is imported.
- The manifest's `dockerfile` is a path from the manifest directory to the Dockerfile in the source tree. Flisk builds bring-your-own with the manifest directory as the build context, so `COPY` paths in an imported Dockerfile may need adjusting. The plan says so.
- Environment variable names are listed; values are never carried, because they may be secrets.
